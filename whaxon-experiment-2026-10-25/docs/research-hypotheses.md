# Research Hypotheses

Each hypothesis is stated so that it can be false, names the test that decides it, and reports the
outcome. Status vocabulary: **supported**, **partially supported**, **rejected**,
**unresolved (blocked)**.

---

## H1 — Scope enforcement is name-based, not destination-based

**Claim.** `ScopeManager.check()` decides on the normalised target string. It never resolves the
name, never re-checks a redirect target, and never constrains sub-requests generated by a tool.
Therefore a scope file that authorises a *name* can authorise traffic to an address outside every
declared CIDR, and a permitted target that redirects can cause an out-of-scope host to be contacted.

**Assumption.** Attackers/operators control both the name presented to the tool and the server's
responses; realistic for both a hostile DNS zone and a compromised in-scope host.

**Competing explanations to exclude.**
- (a) *The check is broken for encoded addresses.* Tested and rejected: decimal, hex, IPv4-mapped
  IPv6, userinfo and fragment forms are all denied (E10 matrix).
- (b) *The validator follows redirects.* Tested and rejected: `_fetch` and `_replay_ctx` both install
  `NoRedirect`; `scripts/scope_experiment.py` observes `ValueError: redirect blocked by validator`.

**Test.** E10 decision matrix (14 target forms) + E11 two-address experiment: `127.0.0.1` in scope,
`127.0.0.2` explicitly out of scope, server A redirects to server B, `ToolRunner.run_tool` executes a
redirect-following catalogue tool.

**Falsification.** If the denied host is never contacted, or if `check()` consults DNS and denies,
H1 is false.

**Result.** **Partially supported.**
- Destination binding: **absent**. `example.com` is allowed while both A records
  (104.20.23.154, 172.66.147.243) are denied by the same ruleset; no resolution occurs.
- Redirect escape: **confirmed**. Server B (out of scope, `127.0.0.2`) recorded a request while the
  scope checker had refused the same URL when given directly (`OutOfScopeError`).
- Redirect hardening in the *validator* path: **present**, so the escape is limited to tool execution
  (and tools' own sub-requests), not to replay verification.
- String-level encoding defences: **sound**.

**Evidence.** `evidence/scope/decision-matrix.json`, `evidence/scope/redirect-escape.json`,
`tests/test_research_observations.py::test_redirect_moves_a_permitted_tool_request_out_of_scope`.

## H2 — The ffuf adapter fabricates HTTP status evidence

**Claim.** ffuf's silent mode prints bare paths. `FfufAdapter.parse` assigns `status = 200` when no
status is present and `size = None`. Findings therefore carry a status code that was never observed,
and the severity ladder (`200 → low`, `403 → info`) is driven by that invented value.

**Test.** E9: synthetic silent/default/404 input; parse the repository's shipped DVWA artefact and
compare ffuf vs gobuster statuses on the same paths in the same engagement; adjudicate against the
live target.

**Falsification.** If silent-mode input produces findings without a status, or with `status=None`,
H2 is false.

**Result.** **Supported.**
- Synthetic: `{"path": "admin", "status": 200, "size": None}` from a line containing only `admin`.
- Shipped artefact: all 12 ffuf `found_path` findings have `status=200`, all 12 have `size=null`;
  9 of 12 paths disagree with the gobuster job in the same engagement.
- Live adjudication (12 paths, 2026-10-25): ffuf's constant `200` matches the measured status on
  5/12; gobuster matches on 10/12. Two gobuster "misses" (`index.php`, `phpinfo.php`: 302 vs 200)
  are cross-deployment differences in the login gate, not adapter defects — noted so the comparison
  is not overstated.
- Aggravating factor found while extracting this: `unique_findings` deduplicates by kind+path and
  keeps the **first ingested** tool's data, so gobuster's contradicting measurement is dropped from
  the canonical view while `count` still records that two tools saw it.

**Evidence.** `evidence/adapters/fidelity.json`,
`tests/test_research_observations.py::test_ffuf_adapter_invents_status_200_when_input_has_none`,
`::test_shipped_proof_artefact_contains_cross_tool_status_contradiction`.

## H3 — Replay verification is neither sound nor complete enough to justify "verified"

**Claim.** (i) A `verified` label can be produced without any exploitable condition; (ii) genuinely
exploitable conditions are labelled `candidate` and sometimes `refuted`; (iii) the two replay paths
disagree on identical evidence.

**Test.** E8: 12-case labelled local benchmark, WHAXON's own `Validator`, both paths, scored with
TP/FP/FN/TN, TPR, FPR, precision, Youden's J.

**Falsification.** If no non-vulnerable case is labelled `verified`, and every exploitable case that
the tool can reach is labelled `verified`, H3 is false.

**Result.** **Supported.**

| Metric | Legacy query-parameter path | Hardened context path |
| --- | --- | --- |
| TP / FP / FN / TN | 2 / 2 / 4 / 4 | 2 / 1 / 4 / 5 |
| TPR (recall) | 0.333 | 0.333 |
| FPR | 0.333 | 0.167 |
| Precision | 0.500 | 0.667 |
| Youden J | 0.000 | 0.167 |

Specific counterexamples, each reproducible:

1. **False positive, both paths.** `marker_decoy` is not injectable; it prints
   "Database driver error: postgresql backend unavailable" for any unrecognised value. Verdict:
   `verified`, reason `marker 'postgresql' appeared only after injection`. The marker list is a
   list of *words*, not a causal test.
2. **False positive, legacy path only.** `timing_decoy` sleeps 3.2 s without any injection. Verdict:
   `verified`, reason `timing delta (median of 3) 3.20s >= 3.0s`. The context path correctly says
   `candidate` — the two paths disagree on identical observations.
3. **Wrong negative label.** `sqli_union` is exploitable via `UNION SELECT`. Verdict: **`refuted`**,
   reason "response identical to baseline" — i.e. the tool asserts the finding is false because its
   own payload did not fire. `refuted` is a stronger claim than "not tested" and is emitted from a
   single non-event.
4. **Payload selection defect.** `PayloadLoader.get_payloads("sqli")[0]` is `` `+HERP `` — a MongoDB
   snippet lifted from a documentation code fence. For `lfi` and `command_injection` the first
   "payload" is `<?php`; for `ssrf` it is `url = input("Enter URL:")`; for `crlf_injection` it is
   `HTTP/1.1 200 OK`. `validate()` always replays index 0, so kind-level precision is decided by
   documentation layout.
5. **Structural completeness.** LFI is not in `REPLAYABLE` at all (22 vendored payloads, no replay
   path); POST-only command injection is rejected by design ("automatic replay of POST is disabled").
   The live, independently confirmed RCE on the target (F3) would therefore never be `verified`.

**Evidence.** `evidence/benchmark/{results,confusion}.json`, `evidence/benchmark/access-log.jsonl`
(proof of what the validator contacted), `tests/test_research_observations.py` validator tests.

## H4 — The web-application boundary falls to `www-data`, not root

**Claim.** Unauthenticated command injection yields code execution as the web server's service
account inside the target container; no privilege escalation is demonstrated.

**Test.** E6/`F3`: `POST /vulnerabilities/exec/` with `ip=127.0.0.1;id`; independent re-test with
`curl`.

**Falsification.** If `id` returns `uid=0`, or returns nothing, the claim changes.

**Result.** **Supported.** `uid=33(www-data) gid=33(www-data) groups=33(www-data)` from two
independent clients; benign control (`ip=127.0.0.1`) produced normal ping output and no `uid`.

**Evidence.** `evidence/live/confirm.json`, `evidence/live/exec_inject_post.body`,
`evidence/verification/verification.json` F3.

## H5 — The deployed instance exposes DVWA modules without authentication

**Claim.** The deployment serves vulnerability modules to unauthenticated clients: LFI, reflected
XSS, command injection, `phpinfo.php`, and the destructive `setup.php` control.

**Competing explanation.** The client holds a session that happens to be authenticated.

**Test.** Every probe used a fresh process/session; each response's footer reports
`Username: Unknown`; the independent `curl` run in `verify_findings.py` carries no cookie jar at all.

**Result.** **Supported.** 6/6 findings re-confirmed with a cookieless client.

## H6 — The target's DVWA database is uninitialised, so stateful modules cannot be assessed

**Claim.** `login` succeeds but every DB-dependent module fails; the `sqli` module returns a PHP
fatal error naming `dvwa.users`.

**Test.** Login redirect to `setup.php`; `sqli?id=1` → 461-byte
`Uncaught mysqli_sql_exception: Table 'dvwa.users' doesn't exist`.

**Result.** **Supported.** Consequence: SQL injection, brute force, stored XSS, CSRF and weak
session IDs could not be assessed live. Resetting the database was prohibited (shared host), so H7
below stays **unresolved**.

## H7 — WHAXON's SQLi verification would fire on a genuinely injectable DVWA

**Claim under test.** On DVWA low, `validate()` would mark a real SQL injection `verified`.

**Result.** **Unresolved / contradicted on the benchmark.** Live testing is blocked by H6. On the
benchmark (`sqli_low`, which reproduces DVWA-low's error text), the verdict is `candidate`, because
the replayed payload `` `+HERP `` contains no quote. This does not prove what WHAXON would do against
a working DVWA, but it falsifies the general claim that a genuine injection implies `verified`.

---

## H8 — The verification engine would be more trustworthy if it resolved and pinned destinations

**Status.** **Not tested as an intervention** (the study is observational; no patch is proposed or
merged). Evidence for the direction: the `_replay_ctx` path already blocks redirects, pins host+port
and downgrades timing-only evidence, and on the same benchmark it scores FPR 0.167 vs 0.333. That is
a within-tool natural experiment, not a controlled trial, and is labelled as such.
